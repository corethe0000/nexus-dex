NexusSwap contract guide

1. In short

NexusSwap holds one side of an atomic swap between Nexus and an EVM chain. A lock holds an ERC-20 token or the chain's own coin for a fixed recipient until a deadline. Whoever shows the secret behind the lock's hash before the deadline pays the recipient; after the deadline anyone can return the coins to the sender. The Nexus side of the same swap is a Tritium DEBIT locked to the same hash.

Properties that matter for users
  • A claim always pays the lock's recipient, a refund always pays its sender. Nobody, including whoever sends the transaction, can redirect them. The only exceptions are made by the owners themselves: the recipient may claim to another address of its own (claimTo), the sender may refund to another address of its own (refundTo).
  • Anyone may send a claim (with the secret) or a refund (after the deadline). That is what lets the relay's watcher and independent keepers finish a swap for someone whose page is closed.
  • The contract holds no state other than the locks. Once deployed it cannot be changed or stopped.

2. A lock from start to end

  1. lock: the sender moves the amount into the contract. The lock records sender, recipient, token, amount, hashlock and deadline. Its id is the hash of all of these plus a swap reference, so the same lock cannot be made twice.
  2. claim: before the deadline, with the secret whose SK256 hash is the hashlock. The secret is published in the Claimed event; that is how the other side of the swap learns it.
  3. refund: from the deadline on, if nobody claimed. Returns the full amount to the sender.

A claim and a refund can never both happen: a claim needs now < deadline, a refund needs now >= deadline, and each moves the lock out of Open for good.

Errors

BadParams (zero recipient or amount, deadline in the past or over 30 days), AlreadyExists, WrongValue (native coin value does not match, or value sent with a token), NotOpen, Expired, NotExpired, WrongSecret, TransferFailed (token call failed, or a token delivered less than the amount), NotRecipient, NotSender, Reentered.

4. The hash: SK256, the same as on Nexus

The Nexus side of a swap is a DEBIT whose condition checks SK256(state of the reveal register) == hashlock, using the Nexus opcode OP::CRYPTO::SK256 (Skein-256 with the Nexus parameters). NexusSwap checks the same SK256 hash in Solidity (Sk256.sol, a pure library), so one secret opens both locks. The library is tested against vectors produced by the Nexus wallet code from the same secrets.

Most of the roughly 310,000 to 320,000 gas a claim uses goes to this hash. That is the price of using the hash Nexus has, instead of adding a new one to the Nexus core.

5. Tokens

  • Tokens that return nothing (USDT on Ethereum): every token call goes through a check that accepts no return data or a true return value, and refuses a call to an address without code.
  • Fee-on-transfer tokens are refused. The contract measures what arrived; if it is not exactly the amount, the lock fails. A lock always holds what both sides agreed on.
  • Frozen addresses (USDT and USDC can freeze one): a frozen recipient uses claimTo, a frozen sender uses refundTo. If the contract itself were frozen by a token issuer, every lock of that token would stay stuck; nothing in the contract can prevent that, so the site lists only plain stablecoins and the native coin.
  • Re-entry: lock, claim and refund refuse to be called again while one of them runs (a transient storage flag, EIP-1153). State is always updated before coins move.

7. How it was tested

Unit tests (Foundry)

Lock, claim and refund for tokens and the native coin; wrong secret, early refund, late claim, double claim, re-entry from a token hook, a token that returns nothing, a fee-on-transfer token (refused), claimTo and refundTo only by their owner, the 30 day cap, and the SK256 hash against the wallet's vectors.

Forks of the five mainnets

contracts/test/Fork.t.sol deploys NexusSwap on a local copy of each mainnet (nothing is sent to the real chain) and runs lock, claim, and lock, refund with the real token contracts and with the native coin. It also checks the decimals of each address in the list. Run on 16 November 2026, all passed:

Public testnets and the full swap

End-to-end swaps through the website on Sepolia and BSC testnet (MetaMask on one side, a maker on the other), including a refund after the deadline; and many more on a private Nexus chain with a local EVM chain: both directions, either side stopping, the watcher and the keeper finishing for a closed page, claim to another address when the recipient cannot receive.

The current version runs on the public testnets since 16 November 2026: BSC testnet 0x86948d0c9612d6fe2f44548c9aad1db53c2aa335, Sepolia 0xddacddede45a337f487fd917d52e0570a24a15f9, the code on both equal to the build.

8. Deploying on mainnet

Everything below is scripted and was rehearsed on 16 November 2026 on a fork of each of the five mainnets: the deploy went through and the code on chain matched the build (code hash 0x942e52b3...c5adc9 on all five).

Gas prices move; the script prints the cost at the time of the deploy. A whole swap on the EVM side (approve, lock, claim) is about 650,000 gas in total, well under 1 USD on each of these chains at the prices above.

Steps

  1. Build: cd contracts && forge build (solc 0.8.28, optimizer 200 runs, settings in foundry.toml).
  2. Run the fork check once more: node tools/fork-check.mjs.
  3. Fund a fresh deployer address with the cost above plus a margin. Its key goes in a file only the deploy reads.
  4. See the cost: CHAIN=56 DEPLOYER_KEY_FILE=key.txt ESTIMATE=1 npx tsx tools/deploy-mainnet.ts (from service/).
  5. Deploy: the same without ESTIMATE=1. The script checks the RPC is on the right chain, waits for the receipt, compares the code on chain with the build, and writes contracts/mainnet/deployments/56.json (address, first block, transaction, deployer, code hash). It refuses to deploy twice on a chain.
  6. Publish the source: ETHERSCAN_API_KEY=... sh tools/verify.sh 56. One Etherscan API key covers Etherscan, BscScan, PolygonScan, Arbiscan and BaseScan. Without a key, upload mainnet/NexusSwap.standard-input.json on the explorer's Verify and Publish page (compiler v0.8.28, standard JSON input).
  7. Write the settings: node tools/configs.mjs turns the deployments into the site's mainnet profile, the relay's chains and the keeper's chains (in mainnet/config-out/).
cd contracts && forge build && node tools/fork-check.mjs
cd ../service
CONTRACTS=../contracts/out CHAIN=56 DEPLOYER_KEY_FILE=key.txt ESTIMATE=1 npx tsx tools/deploy-mainnet.ts
CONTRACTS=../contracts/out CHAIN=56 DEPLOYER_KEY_FILE=key.txt npx tsx tools/deploy-mainnet.ts
cd ../contracts && ETHERSCAN_API_KEY=... sh tools/verify.sh 56 && node tools/configs.mjs

The deployer has no role after the deploy: the contract has no owner. Its address only shows who deployed it.

9. Reviews and what is still open

  • Internal security reviews (several rounds, the last on 16 November 2026, with separate reviewers per part). Findings were checked against the code and fixed: among them the fee-on-transfer refusal, refundTo, the 30 day cap, the re-entry guard and the claim checks before sending.
  • No outside audit yet. Recommended before mainnet; the scope is NexusSwap.sol (about 200 lines) and Sk256.sol (about 250 lines), plus the swap timing rules in the off-chain code that decide when each side may act.
  • Open before mainnet: the confirmations per chain (section 6).
